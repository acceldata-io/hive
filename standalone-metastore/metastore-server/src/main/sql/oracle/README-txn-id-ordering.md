# Oracle TXN_ID ordering: a required manual step for existing metastores

This build declares the Oracle `TXNS.TXN_ID` generator `ORDER`. Fresh installs and schemas created by
the upgrade scripts get that automatically. **An Oracle metastore that already exists does not, and
stays exposed to silent data loss on reads until a DBA runs the remediation script below.**

## What goes wrong without it

Oracle defaults sequences and identity columns to `NOORDER`. With `NOORDER` and a cache, each database
instance serves transaction ids from its own cached block, so ids stop increasing with time: a
transaction started later can receive a lower id than one started earlier.

The metastore's visibility rule is that a reader treats every transaction id above its own high water
mark as not yet committed. An out-of-order id therefore places an already committed writer above a
later reader's high water mark, the writer's write id is reported as still open, and the reader skips
that writer's files. The query returns fewer rows, or none at all, **and raises no error**. Nothing in
the logs marks it as a failure, which is what makes it expensive to diagnose.

This matters most on RAC, where multiple instances each hold their own cache. A single instance is far
less exposed, because one instance hands ids out in order, but the generator is still declared
`NOORDER` and will misbehave the moment a second instance is added.

## Who has to do something

| Situation | Action |
|---|---|
| Fresh install on this build | none, the schema is created `ORDER` |
| Existing Oracle metastore, RAC or multi-instance | **run the remediation script** |
| Existing Oracle metastore, single instance | run it, so adding an instance later is safe |
| MySQL, Postgres, SQL Server, Derby | none, this is Oracle specific |

The remediation is deliberately not part of the automated upgrade chain. It alters the id generator of
a live metastore, which is a DBA decision and needs to be scheduled and verified rather than applied
silently by a schema tool.

## How to check whether you are exposed

Run as the metastore owner, or as a DBA with `metastore_owner` set to that schema. `ORDER_FLAG = N`
means exposed.

```sql
-- upgraded schemas use a named sequence
SELECT sequence_name, cache_size, order_flag
  FROM all_sequences
 WHERE sequence_owner = UPPER('&metastore_owner') AND sequence_name = 'TXNS_TXN_ID_SEQ';

-- schemas created fresh use an identity column with a system generated sequence
SELECT i.table_name, i.column_name, s.sequence_name, s.cache_size, s.order_flag
  FROM all_tab_identity_cols i
  JOIN all_sequences s
    ON s.sequence_name = i.sequence_name AND s.sequence_owner = i.owner
 WHERE i.owner = UPPER('&metastore_owner') AND i.table_name = 'TXNS';
```

## How to remediate

Run the shipped script, which reports what the schema currently has and then prints the exact
statement for that schema. It changes nothing by itself:

```
sqlplus / as sysdba
SQL> ALTER SESSION SET CONTAINER = <your PDB>;      -- only on a container database
SQL> DEFINE metastore_owner = 'HIVE'                -- your metastore schema
SQL> @remediate-txn-id-sequence-order.oracle.sql
```

The script ships in the same directory as the schema and upgrade scripts, under
`hive/scripts/metastore/upgrade/oracle` in an installed cluster. It is not inside a jar.

There are two forms because there are two generator types, and applying the wrong one fails rather
than silently doing nothing:

```sql
-- named sequence, on schemas built by the upgrade scripts
ALTER SEQUENCE <owner>.TXNS_TXN_ID_SEQ ORDER;

-- identity column, on schemas created fresh. The backing sequence is system generated, so
-- ALTER SEQUENCE on it raises ORA-32793 and the change has to go through the column.
ALTER TABLE <owner>.TXNS MODIFY (TXN_ID GENERATED BY DEFAULT AS IDENTITY (ORDER));
```

Do not add `START WITH` to the identity form. The only form available there is
`START WITH LIMIT VALUE`, which restarts the generator from the highest value currently in `TXNS`, and
`TXNS` is pruned continuously: ids far above the surviving rows are still referenced by
`TXN_TO_WRITE_ID` and `COMPLETED_TXN_COMPONENTS`, so restarting from the table maximum can reissue ids
that are already in use.

## What it costs, and how to undo it

Both statements are online metadata changes. They take effect on the next id allocated, need no
metastore restart, no downtime and no data change, and reverse with `NOORDER`.

On RAC, `ORDER` makes the instances coordinate allocation instead of each serving from its own cached
block, so allocating a transaction id becomes somewhat slower. That cost is the point of the change,
and at metastore transaction rates it is not a throughput concern. The cache size is left alone.

## How to verify afterwards

`ORDER_FLAG` must read `Y` for the generator the detection queries reported, with the cache unchanged.
Ids allocated after that are increasing with time; running a few statements and reading the top of
`TXNS` is enough to see it:

```sql
SELECT "TXN_ID" FROM "TXNS" ORDER BY "TXN_ID" DESC FETCH FIRST 5 ROWS ONLY;
```

## Oracle version compatibility

The change adds a clause to statements this schema already used; it does not raise the minimum Oracle
version. `ORDER` and `NOORDER` are part of the same `identity_options` clause that introduced identity
columns in Oracle 12.1, so any release able to run the previous `GENERATED BY DEFAULT AS IDENTITY`
statement accepts this one. On the plain sequence used by the upgrade script, `ORDER` predates 11g.
All four forms this change touches were executed against Oracle 19c Enterprise Edition and confirmed
to report `ORDER_FLAG = Y`.
